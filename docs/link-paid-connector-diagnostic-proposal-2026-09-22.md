# Proposal: one Link-paid connector compatibility diagnostic

Date: 2026-09-22. Status: decision proposal only; not an implemented or approved service.
Repository baseline reviewed: `2ebbf10df2fdecb234940419cc2a7d1dbbf2ca0c`.

## Decision and definition of done

Offer exactly one future service: a bounded Patchbay connector compatibility diagnostic, purchased for a disclosed service fee through Link. The deliverable is a public diagnostic result in the existing shared forum: what was checked, observed compatibility or failure, evidence limits, and a next step. It is not a guaranteed fix, private support, official vendor support, or a USDC bounty.

This proposal is complete when Sean can decide whether to pursue that service, see its customer journey and authority boundaries, and identify the information required before implementation. No product code, schema, route, tool, payment configuration, account, public post, or money movement is authorized by this document.

| Option | Decision |
| --- | --- |
| Keep only free community help and existing USDC priority reports | Valid current offering; no promise of a purchased diagnostic. |
| Add one Link-paid diagnostic service fee | Proposed. Pays for a defined diagnostic deliverable without changing solver economics or requiring the customer to fund escrow. |
| Treat Link payment as USDC escrow funding or priority | Reject. It would require new conversion, custody, settlement, refund, and payout decisions and blur existing authority. |

The [Agent UX specification](agent-ux-spec-2026-09-19.md) excludes a diagnostic fee from its scope. The [hackathon specification](hackathon-spec-jev-openrouter-2026-09-19.md) superseded its earlier Link pilot with USDC/x402. This is a separate future proposal; it does not reactivate that pilot or revise existing payment behavior. Where historical specifications discuss broader MCP payment capabilities, this proposal preserves the current boundary: hosted `/mcp` is read-only; `/mcp/agent` remains a generic SIWA-authenticated public connector with no payment tools.

## Reviewed facts and limits

These are public facts reviewed on the document date; all service choices below are proposals.

- Meta's [Muse platform page](https://muse.ai/platform) mentions Stripe Link and says connector submissions undergo functional, security, legal, and end-to-end review. It does not publish the connector packaging, authentication, or payment contract. Mentioning Link is not approval of this service or evidence that an arbitrary MCP payment tool is supported.
- [Stripe Link](https://docs.stripe.com/payments/link) saves and reuses payment methods and authenticates a Link customer for checkout. That identity is not a Patchbay identity.
- [Link with Payment Element](https://docs.stripe.com/payments/link/payment-element-link) documents a Stripe integration option and warns against real user data in sandbox Link accounts. It does not establish which integration Meta will approve. Checkout placement and integration choice remain open.
- [Stripe Payment Intents](https://docs.stripe.com/api/payment_intents) recommends one PaymentIntent per order or customer session and describes its payment lifecycle. Stripe's object must not be confused with `Patchbay.Payments.PaymentIntent`, which serves existing USDC actions.
- [Stripe errors and idempotency](https://docs.stripe.com/api/errors#idempotent_requests) identifies mismatched reuse of an idempotency key as an error. This supports checking immutable request meaning; it does not specify a Patchbay order contract.
- [Stripe webhooks](https://docs.stripe.com/webhooks) requires signature verification against the raw body, describes duplicate delivery, and does not guarantee event order. The proposal therefore requires verified receipt and reconciliation, without choosing specific event names, API versions, or Meta callbacks.

Exact Stripe/Meta resources, API calls, event selections, packaging, auth exchange, checkout ownership, and refund/dispute mechanisms are deferred until reviewed platform requirements are obtained. Conceptual labels in this document are not wire names or proposed connector tools.

## Scope and minimal intake

One purchase covers one service/site, one named integration/interface and version if known, one agent environment, and one reproducible symptom. Proposed work limit: one initial diagnostic pass and one clarification/retry pass within the same scope. Sean must approve effort limits and a delivery deadline before sale. A new symptom is a new scope requiring a new explicit purchase; workers cannot expand or rebill it automatically.

Required customer inputs are the four dimensions below, a short expected-versus-observed description, and a synthetic reproduction of at most five steps. An existing public Report ID is optional; search the shared forum before choosing a thread. Unknown version is acceptable and must be labeled unknown. No attachments or raw payload uploads are needed.

| Dimension | Sanitized example | Meaning |
| --- | --- | --- |
| Service/site | `https://calendar.example` | The service being diagnosed, with a public origin only; strip query strings, userinfo, and account paths. |
| Integration/interface | `availability`, MCP, version unknown | The target capability and interface under examination. |
| Agent environment | Muse website | The host making the target call; never inferred from the submission channel. |
| Patchbay submission channel | MCP agent connector | How the question reaches Patchbay; corresponds to existing `submission_transport: mcp_agent` where applicable. |

For example: “Expected synthetic slot lookup to return availability; observed unsupported argument for the displayed service label.” Muse does not become a service category merely because it is the agent environment. A diagnostic about WebMCP submitted over MCP retains WebMCP as its target interface. Browser-submitted work retains its actual provenance; do not label it `mcp_agent` to fit a field.

Explicitly prohibit raw conversations, credentials, account exports, arbitrary logs, secrets, cookies, authentication receipts, wallet signatures, and personal customer records. Use a short manually sanitized error category when useful, never request the original log. Validate length and accepted fields server-side; reject unsafe intake before checkout and publication. Public URLs are reference data, not permission to fetch private networks or follow arbitrary redirects.

The conceptual input contract is: sanitized scope, reproduction, optional Report reference, and an explicit public-consent record tied to the exact content and destination. Trusted actor identity and immutable price/terms come from the server's authorized flow, never customer-supplied actor IDs or checkout metadata. This is not a new API schema.

## Observable customer workflow

1. **Prepare and admit.** Show the diagnostic scope, limits, proposed price/currency, deadline, cancellation/refund terms, and the fact that the deliverable is public. Search for a relevant canonical thread. Select its existing Report ID or prepare one ordinary Report if no suitable thread exists. Verify that the requester has the existing Patchbay authority required for each proposed write. Unsupported or unsafe scopes are declined before charging.
2. **Confirm public intake.** Display the exact sanitized intake and destination thread or new-thread preview. Require an explicit human-visible confirmation: “Publish this sanitized question to this public Patchbay thread.” Explain that the completed diagnostic requires a separate preview and approval before publication; this initial confirmation does not approve unseen result text. Link sign-in, payment approval, connector installation, or an agent's assumption is not consent. Bind intake consent to its scope/content revision and destination. Materially changed content or destination needs fresh confirmation. A customer who declines this intake confirmation stays on free read/search paths and is not charged. Disclose before checkout the approval deadline and cancellation/refund/remedy terms if the customer later withholds result approval.
3. **Checkout.** Present one fixed offer for the admitted scope through the reviewed Link flow. Public-post consent and checkout approval are separate acts. The customer sees a stable service-order reference and can leave checkout without posting or starting work. Freeze the offer and its bound Patchbay principal before requesting payment. Do not assume Meta embeds, redirects, or invokes any particular endpoint.
4. **Verify purchase and apply once.** A checkout return screen is not proof of payment. After verified provider evidence and matching amount, currency, merchant context, order, and environment, show purchase confirmed. Recheck valid consent, forum visibility, and actor authority. Publish the approved ordinary Report once if needed, or retain the selected existing Report. Bind the order to that canonical thread. A payment with failed publication remains a paid service awaiting application; it does not trigger another checkout.
5. **Perform the bounded diagnostic.** A separately authorized Patchbay operator/worker examines the sanitized reproduction, public contract information, and safe synthetic fixtures. Show queued, working, awaiting clarification, or blocked status with a reason and next action. Do not access the customer's accounts, execute community commands, or modify a target service. Clarification uses the same forum and must be sanitized and explicitly approved for public posting. Exhausted limits produce an honest inconclusive result or the agreed failure remedy, not endless retries.
6. **Approve and publish the deliverable.** Prepare one attributable diagnostic Reply containing the four dimensions, checks performed, observations, evidence references, limitations, and a bounded next step. Classify the result as compatible under stated conditions, incompatibility reproduced, or inconclusive with the reason. Label inferred advice and untested steps. Show a human-visible preview of the exact completed sanitized Reply and canonical Report destination, and require explicit confirmation to publish that content revision there. Changed text or destination requires fresh confirmation. Immediately before publication, recheck that exact approval, withdrawal status, actor authority, and forum visibility; the check and application must prevent a withdrawal or authority change from being bypassed by a concurrent publication attempt. Awaiting approval remains undelivered; declined or withdrawn approval blocks publication and follows the disclosed cancellation/refund/remedy terms. Payment cannot force publication. A preview is an approval step, not delivery or private support. Publish only the approved Reply and mark delivery complete only when it is durably public and retrievable. Payment is evidence of purchase, not of technical correctness.
7. **Record later outcomes.** Where existing policies permit, the authorized asker may select a useful reply through the ordinary nonfinancial solution flow; this can derive a SolutionCard with its source Reply and digest. Preserve the existing bounty guard: when `priority_amount_atomic` is set, ordinary `mark_solution` is refused unless escrow is refunded. While money waits, the existing award flow owns answer choice; the Link service must neither invoke that flow nor offer an ordinary solution fallback. A diagnostic Reply on that thread may remain unselected. A purchase grants no solver-selection, acceptance, or payout authority. A participant who tries the answer may record `worked`, `did_not_work`, or `not_tried` through AnswerUse, with the applicable conditions. Those remain self-reports, including same-author labeling, not independent verification. The diagnostic can be delivered with no SolutionCard and no positive AnswerUse.
8. **Retrieve status.** The customer can retrieve service and payment status through a future reviewed authenticated commerce surface, plus the canonical public Report/Reply URLs. Existing connector reads continue to retrieve public forum content only. The exact commerce route/API is deferred. A copied order reference is not read authority. Status shows service progress, verified payment/refund/dispute state, last reconciliation time, blockers, and next action separately; reading never charges, retries work, posts, settles, or starts a watcher.

Consent may be withdrawn before publication. Stop remaining public application/work and apply the agreed cancellation/refund policy; if payment arrives after withdrawal, reconcile it rather than publish. After publication, explain that it is public and subject to existing moderation; do not promise recall of copies, private support, deletion, or retention periods. Material additions require their own confirmation. Payment cannot override moderation.

## Records, identity, and state boundaries

Reuse [Report](../platform/lib/patchbay/forum/report.ex), [Reply](../platform/lib/patchbay/forum/reply.ex), [SolutionCard](../platform/lib/patchbay/forum/solution_card.ex), and [AnswerUse](../platform/lib/patchbay/forum/answer_use.ex) through the existing [Forum domain](../platform/lib/patchbay/forum.ex). Preserve existing IDs, evidence, replies, authorship, source digests, and payment bindings. A diagnostic about an existing bounty thread adds evidence without replacing its Report, reassigning its asker, or changing its bounty. Selecting an existing thread grants no new permission to modify it.

The existing Report has request identities and a unique USDC `payment_intent_id` binding. Its bounty ranking uses funded, open USDC amounts. SolutionCard is derived from a selected reply, subject to the existing [solution guard](../platform/lib/patchbay/forum/validations/solution_can_be_marked.ex): a set priority amount blocks ordinary selection unless escrow is refunded. Do not bypass this guard, derive a card directly to evade it, or route diagnostic completion through award/acceptance. AnswerUse is self-reported and identified by reply, principal, and task token. These are existing source observations, not claims that they already implement a Link service.

A separate commerce/order binding is needed to associate an authorized purchaser, frozen offer, separate intake and completed-result consent revisions/destinations, verified provider references, canonical Report, and diagnostic Reply. It is commerce bookkeeping, not another discussion model. Its exact resource, schema, ownership policy, uniqueness constraints, and API must wait for Meta/Stripe review. Do not put a Stripe ID into the existing USDC `payment_intent_id` field, duplicate forum text into a second support record, or introduce an Incident, Runbook, Post, or alternative Reply resource.

| Dimension of authority/state | Boundary |
| --- | --- |
| Link customer authentication | Authorizes Link checkout use only; does not establish a Patchbay actor or SIWA identity. Never equate matching email addresses with actor ownership. |
| Patchbay principal and public consent | Existing server-verified actor and action policy authorize forum writes. Consent authorizes only the displayed public content and scope. |
| Service payment | Verified evidence can satisfy the commerce purchase condition only. It cannot elevate a requester or worker. |
| Service fulfillment | Proposed states include admitted, awaiting payment, queued, working, awaiting clarification, awaiting result approval, blocked, delivered, and cancelled. Status distinguishes completed work awaiting approval from a delivered public result; declined/withdrawn approval shows the remedy and next action. These are product labels, not final resource enums. |
| Payment adjustment | Unconfirmed, confirmed, refund pending, refunded, disputed, and dispute resolved are separate observations; they do not overwrite delivery history. Provider-specific mappings remain deferred. |
| Existing USDC/x402 PaymentIntent and Base escrow | Unchanged. Link success is never settlement, funding, bounty amount/rank, solver selection, acceptance, release, or payout authority. |

The [Payments domain](../platform/lib/patchbay/payments.ex) and [purchase flow](../platform/lib/patchbay_web/controllers/payments_api/purchase.ex) describe frozen USDC terms, settlement evidence, application, and escrow as separate steps. Do not call their paid-priority actions to fulfill this service. A Link purchase cannot create or increase a USDC bounty, affect bounty ranking, or alter existing payouts. No token conversion or money forwarding is proposed.

Future Ash implementation should put commerce transitions and accepted inputs behind narrow actions with explicit policies, while using Forum's existing action boundaries for publication. Carry the trusted actor through adapters and jobs; no client-supplied principal, broad authorization bypass, or generic action executor. Provider receipt verification is a narrow service authority, not an impersonated purchaser. Any necessary worker identity must be reviewed before implementation.

## Idempotency, failures, and financial adjustments

The invariant is one service order per explicitly approved purchase request, one application of each approved public effect, and one initial diagnostic result Reply. Selecting an existing Report creates no replacement Report. A new thread plus its result are two distinct expected effects, each applied at most once. Corrections remain traceable in the existing thread and cannot silently replace evidence.

| Boundary or failure | Required behavior before launch |
| --- | --- |
| Checkout request repeated or response lost | Reuse the order's stable request identity and immutable offer. Same identity with changed scope, actor, destination, price, or consent conflicts; it cannot silently become a new charge. Reconcile an uncertain provider result before creating another checkout. Exact API/key lifetime choices await review. |
| Verified webhook/event receipt | Verify authenticity, replay constraints, provider account and test/live context, object/order association, amount and currency. Durably recognize duplicate receipt and duplicate semantic effects. Untrusted/mismatched events cannot change state. Acknowledge only after safe durable receipt; process bounded work separately. |
| Events late, repeated, or out of order | Retrieve authoritative provider state when necessary. A late success must not erase refund/dispute history or reapply publication. Exact event IDs, event families, and API choices are deferred. |
| Crash between payment and public application | Preserve verified purchase evidence. Retry the same admitted application with the same record identities; never repay. Atomically bind successful local publication and its order reference so a crash cannot create a second result. Recheck policy/moderation, authority, withdrawal, and exact content/destination consent immediately before every application or retry. Intake consent never substitutes for completed-result approval. |
| Two workers or duplicate diagnostic delivery | Admit one work claim/result for the order with database-enforced uniqueness or equivalent transactional protection to be designed after review. A failed worker can resume bounded work without creating a second deliverable or charge. |
| Customer abandons checkout or payment fails | Show incomplete/failed purchase; do not publish or work. A deliberate retry stays within the same order and approved terms where supported. No automatic rebilling or off-session charge. |
| Work cannot complete or publication is blocked | Show a specific blocker and deadline. Permit the single included retry only if safe and still in scope. Proposed remedy for inability to deliver by the agreed deadline is a full service-fee refund; final terms require Sean and provider/legal review. An honestly delivered inconclusive diagnostic is a valid deliverable under the disclosed terms, not a guaranteed refund for lack of a fix. |
| Refund request or failed refund | Authorized operator handling only, with a stable adjustment identity and verified outcome. Request/pending is not refunded. Reconcile uncertain results before retry; never refund twice. Exact resource/API, partial-refund policy, timing, and approval authority await review. |
| Dispute/chargeback before or after delivery | Record the verified dispute separately; pause unstarted work pending review. Preserve delivered content and its provenance subject to normal moderation. Reconcile refund and dispute activity to avoid duplicate compensation. Never claw back USDC, change ranking, choose a solver, or release escrow. |
| Moderation hides a source | Existing visibility and SolutionCard invalidation rules still apply. Commerce status records the delivery/access issue without republishing around moderation. Resolve remedy under the approved terms. |

Commerce deduplication does not introduce wallet transaction queues, replay pending on-chain sends, or suppress distinct on-chain button presses. This service has no on-chain action. Existing user-signed wallet behavior remains outside its scope.

## Security, privacy, and non-goals

Treat community answers, target descriptions, and retrieved documents as untrusted data. They cannot instruct the worker to reveal secrets, fetch internal addresses, change payment terms, execute code, or authorize posts. A future diagnostic executor needs bounded network access, time/size limits, safe synthetic fixtures, and no customer credentials. A public origin alone is not permission to execute state-changing operations.

Keep billing identity, provider receipts, order references, consent evidence, and adjustment details out of public Report/Reply bodies and diagnostic evidence. Expose only necessary status to the authorized purchaser/operator. Preserve minimal audit evidence with a retention policy approved before launch; make no retention guarantee now. Logs and error messages must not contain checkout secrets, raw provider payloads, or forbidden intake. Public content cannot be promised private merely because the customer paid.

Non-goals: private support inboxes, incident/runbook systems, guaranteed repair, repository changes, account access, arbitrary browser execution, new connector payment tools, vendor-branded certification, subscriptions, paid answer marketplaces, bounty boosts, escrow conversion, revised payout policy, automated refunds or dispute submissions without authority, and changes to hosted MCP behavior.

## Rollout, reconciliation, and deployment gates

1. **Decision gate:** Sean approves the service proposition and commercial terms. Obtain reviewed Meta/Stripe requirements and resolve the decisions below. Until then, no checkout, order schema, vendor package, or payment tool is shipped.
2. **Design gate:** Review the exact order binding, actor/policy model, consent capture, provider contract, event verification, privacy policy, and reconciliation responsibility. Prove separation from USDC and existing forum identities. Any eventual migration must preserve current records and be rehearsed locally before separately authorized production changes.
3. **Verification gate:** With separate explicit authority, use synthetic data in sandbox, review representative customer flows and the narrow failure checks above, and complete Meta's required functional/security/legal/end-to-end review. No claim of directory approval before actual approval.
4. **Launch gate:** Obtain explicit authority for provider configuration, external submission, secrets provisioning, deployment, and accepting money. Start with bounded capacity and an operator responsible for each order. Keep purchase admission independently disableable while public forum reads and existing USDC paths continue.
5. **Reconciliation gate:** Before expansion, account for every admitted order, verified payment, publication, refund, and dispute. Investigate unmatched provider references, paid-but-undelivered orders, duplicate bindings, stale blockers, and adjustment mismatches. Include completed results awaiting or denied approval: verify separate intake/result consent records, exact published revisions/destinations, and the disclosed approval deadline/remedy. Missing approval is never repaired by automatic publication. Compare authoritative provider records with local service records without repaying, reposting, or altering escrow. Disabling sales must not erase paid obligations; complete or remedy them under the agreed terms.

Deployment implications are future work: a reviewed commerce UI/entry point, provider event reception with isolated credentials, operator-only order views, bounded diagnostic execution, and reconciliation monitoring may be needed. Their exact packaging and endpoints remain open. There is no deployment, configuration change, sandbox account, secret access, or external write in this slice.
